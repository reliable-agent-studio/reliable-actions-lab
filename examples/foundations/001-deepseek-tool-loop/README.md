# DeepSeek Tool Loop: A Minimal Agent Example

This example demonstrates the smallest useful agent tool loop:

1. a user asks a question;
2. the model decides whether to request a tool;
3. the Python application executes the requested local function;
4. the application returns the tool result to the model;
5. the model turns that result into a user-facing answer.

The purpose is to make the boundary between the **model**, the **API client**,
the **application**, and the **tool implementation** visible. This is a
learning example, not a production-ready agent or a framework benchmark.

## What you will learn

After running the example, you should be able to explain:

- why a model does not directly execute a Python function;
- how a tool schema differs from the real function implementation;
- why tool calling usually requires at least two model requests;
- how `tool_call_id` connects a result to the model's request;
- which responsibilities remain in trusted application code;
- what an agent framework would automate around this loop.

## Architecture

```text
User message
    ↓
Model receives the message and tool schema
    ↓
Model returns a tool name and JSON arguments
    ↓
Python validates the request and executes a local function
    ↓
Python appends the tool result to the conversation
    ↓
Model generates the final answer
```

## Requirements

- Python 3.8 or later (tested locally with Python 3.8.13);
- a DeepSeek API key;
- network access to the DeepSeek API.

This example uses the OpenAI Python client with DeepSeek's OpenAI-compatible
endpoint. The direct dependency is pinned in `requirements.txt`.

## Run

```bash
python order_agent_deepseek.py
```

Expected stages:

```text
[1. MODEL DECISION] Asking the model what to do...
[2. LOCAL TOOL EXECUTION] Looking up ORD-123
[3. MODEL SYNTHESIS] Returning the tool result to the model...

[4. FINAL OUTPUT]
<a friendly order-status answer>
```

Exact wording may vary because the final response is generated by a model.

## Read the code in this order

1. `get_order_status()` — the real local Python function;
2. `tools` — the model-facing function name, description, and JSON schema;
3. `messages` — the system instruction and the user's request;
4. the first model call — tool selection is available;
5. validation and local function execution;
6. the `role="tool"` message linked by `tool_call_id`;
7. the second model call — no tools are offered, so it produces text.

## Learning review: six important questions

### 1. What does the model see?

On the first call, the model receives:

- the `messages` list, including system instructions and the user question;
- the `tools` list, including each public tool name, description, and JSON
  parameter schema.

The model does **not** see the Python function body, API credentials, database
connections, or other private implementation details.

On the second call, this demo sends the expanded `messages` list but does not
send `tools`. The history now includes the original messages, the assistant's
tool request, and the tool result.

### 2. What does a model-generated tool call contain?

A function tool call contains:

- a unique tool-call ID;
- the public tool name;
- concrete arguments encoded as JSON.

Conceptually:

```json
{
  "id": "call_123",
  "function": {
    "name": "get_order_status",
    "arguments": "{\"order_id\":\"ORD-123\"}"
  }
}
```

It does not contain a Python function reference, executable code, or a tool
result. The arguments are model-generated input and must be treated as
untrusted.

### 3. Who actually executes the Python function?

The model **requests** the call. The OpenAI Python client transports and parses
the response. The Python application validates the request and explicitly
executes `get_order_status()`. The model never executes the local function.

In this example the library is a low-level API client, not an agent framework.
An agent SDK can automate the loop and dispatch, but trusted application code
still owns the function, its credentials, and its execution permissions.

### 4. Why is the tool result sent back to the model?

The raw tool result supplies factual data, but it is not necessarily the final
user-facing response. Sending it back lets the model:

- connect the result to the user's original request;
- explain, summarize, or combine results;
- generate an appropriate user-facing answer;
- decide whether more information or another tool is needed.

The second call receives the complete conversation, so it continues the
unfinished original task. No fabricated user message such as "please summarize
this" is needed.

For a fixed response whose exact wording must be guaranteed, application code
can render a template instead of making a second model call.

### 5. Where should tool names and arguments be validated?

Validation must happen in trusted application code **before** dispatching the
tool. This example validates only the allowlisted name:

```python
if tool_call.function.name != "get_order_status":
    raise ValueError(...)
```

A production application should also validate:

- required arguments, types, formats, and permitted values;
- unexpected extra arguments;
- authenticated user and tenant context;
- authorization to read or change the requested resource;
- approval requirements for consequential operations.

The JSON schema helps the model generate suitable arguments, but it does not
replace server-side validation and authorization.

### 6. What happens if the tool succeeds but the process crashes before returning the result?

The immediate effect is that the user receives no final answer. The deeper
problem is that an external action may already have succeeded while the agent
runtime has no durable record of the result. This is an **ambiguous outcome**:

```text
Application calls tool
    ↓
External system commits the action
    ↓
Application crashes before saving or returning the result
    ↓
Recovery logic cannot tell whether the action happened
    ↓
A blind retry may execute the action again
```

For this read-only fake lookup, repeating the call is usually harmless. For a
side-effecting tool such as `issue_refund`, `charge_card`, `send_email`, or
`create_order`, a blind retry can cause duplicate refunds, charges, emails, or
orders.

Common mitigations include:

- a stable idempotency key representing the business operation;
- a durable action receipt saved by call ID and business operation ID;
- querying the external system before retrying an uncertain operation;
- transactional outbox or workflow-state patterns;
- recovery logic that distinguishes `not started`, `committed`, `failed`, and
  `outcome unknown`.

This failure boundary is the bridge from a basic tool-calling demo to Agent
Reliability research.

## Additional design questions

### Why are tools available only on the first model call?

This demo has a deliberately fixed two-stage workflow. The first call may
select `get_order_status`; the second call receives no `tools` parameter and
therefore produces the final text. This avoids a repeated tool call and makes
the basic loop easy to inspect.

A general-purpose agent would keep tools available and loop until there are no
more tool requests, while enforcing maximum rounds, duplicate detection,
validation, permissions, and approval policies in code.

### Should tool dispatch use reflection so it is generic?

Not for this first example. An explicit check makes the trust boundary clear:

```python
if tool_call.function.name != "get_order_status":
    raise ValueError(...)
```

With multiple tools, use an explicit allowlisted registry that maps public tool
names to trusted handlers. Avoid unrestricted `globals()` or `getattr()` based
on model-generated names, because that could expose unintended functions.

### Can a tool hide a complicated implementation?

Yes. The model may see a small interface such as:

```text
get_order_status(order_id)
```

The implementation can call an external API, query a database, apply business
rules, write an audit event, or enqueue a background job. The function should
usually remain a thin, controlled adapter to those services. Credentials,
database clients, authorization context, and internal implementation details
must remain in the application and must not be sent to the model.

### Should the first demo use a longer production prompt?

No. The short prompt is intentional. It establishes the agent's role, tells it
when to use the tool, treats the tool as authoritative, and prohibits invented
status. Missing-order handling, tool failures, retries, multiple tools,
approvals, and generic dispatch should be added as separate experiments so
that each change remains observable.

### Is this the final product architecture?

No. It is the smallest visible tool loop. A production implementation would
add argument validation, structured errors, authentication, authorization,
timeouts, audit logs, retry policy, idempotency, observability, tests, and
durable state where necessary.

## Security and reliability notes

- Treat model-generated arguments as untrusted input.
- Allowlist tool names before execution.
- Keep API keys and database credentials outside model context.
- Do not return stack traces, secrets, or unnecessary customer data.
- Require approval for consequential write operations.
- Do not blindly retry a side-effecting tool after an ambiguous timeout.

## Scope of this example

The fake order-status function is deterministic and has no external side
effects. That is intentional. It isolates the tool-calling mechanism before
later labs introduce API failures, databases, retries, approvals, and recovery.
